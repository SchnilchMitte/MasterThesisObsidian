# Management, Control, Data and Telemetry Planes

## Data plane

Forwards user/application packets according to forwarding state. In experiments, TRex-generated traffic primarily belongs here.

## Control plane

Computes or installs forwarding behavior. In this project, [[06 - SDN/Ryu]] represents a controller-side control-plane component.

## Management plane

Administrative access and management services: SSH, APIs, telemetry collectors, monitoring, orchestration, etc. The project has a dedicated `172.20.202.*` management network.

## Telemetry / observability plane

Not always treated as a formal separate networking plane, but useful architecturally. It contains the pipelines that observe device and traffic state.

## Project relevance

A separate management network can isolate telemetry/control traffic from production traffic. That improves experimental stability but may hide effects found in real deployments where telemetry shares links with user traffic.

This motivates tests comparing:
- dedicated management transport,
- constrained/shared transport,
- increasing node count / telemetry rate,
- failures and congestion.






# Management, Control, Data and Telemetry Planes

The different networking planes describe **logical functions** of the network. They should not be confused with the physical or logical transport networks over which their traffic is carried.

In the current testbed, two separate transport networks exist:

- **Management network:** `172.20.202.*`
    
- **Data network:** `172.20.2.*`
    

The management network is represented by the orange connections in the testbed topology. The red inter-switch links and the high-speed links to the traffic generators belong to the data network.

---

## Data Plane

The data plane is responsible for forwarding actual user or application traffic according to the forwarding state installed on the switches.

In the testbed, this primarily includes the traffic generated by [[Cisco TRex]] and forwarded through the QFX fabric.

Typical path:

```
TRex
  |
  v
QFX ---- QFX ---- QFX
        Data Network
```

The red inter-switch links and the high-speed links between traffic generators and switches carry this data-plane traffic.

The data plane therefore represents the network behavior that is being observed and optimized by the [[Network Digital Twin]].

---

## Management Plane

The management plane provides administrative access to network devices and infrastructure components.

Typical management functions include:

- SSH access
    
- device configuration
    
- orchestration
    
- management APIs
    
- access to monitoring systems
    
- administration of collectors and services
    

The testbed has a dedicated management network:

```
172.20.202.*
```

Examples:

```
NUC1   172.20.202.41
SW01   172.20.202.151
SW02   172.20.202.152
...
```

The orange links in the physical topology represent this dedicated management connectivity.

---

## Control Plane

The control plane determines or installs how traffic should be forwarded.

In this project, [[Ryu]] represents a controller-side component of the control plane.

Conceptually:

```
Ryu
 |
 | SDN control
 v
QFX
```

The control plane and the management plane are not the same thing.

However, **control-plane communication can be transported over the management network**.

For example:

```
Logical function:
Control Plane

Transport:
172.20.202.* Management Network
```

This means that an SDN control message sent from Ryu to a QFX switch is still control-plane traffic even if the packet itself travels through the dedicated management network.

The exact southbound protocol used between Ryu and the QFX switches in the current testbed is still to be verified.

---

## Telemetry / Observability Plane

The telemetry or observability plane is not always considered a formal networking plane in the same way as the data and control planes.

For this project, however, it is useful to treat telemetry as a separate logical function.

The telemetry infrastructure observes the current state and behavior of the physical network.

Examples include:

```
QFX
 |
 | gNMI
 v
Telegraf
```

and:

```
QFX
 |
 | sFlow
 v
GoFlow2
```

The telemetry plane therefore includes information such as:

- device state
    
- interface state
    
- interface counters
    
- CPU and memory utilization
    
- temperature
    
- packet drops
    
- traffic samples
    
- flow information
    
- network topology information
    
- synchronization state
    

---

## Logical Plane vs. Transport Network

An important distinction is:

```
Plane
=
What is the purpose of the communication?

Transport Network
=
Over which network is the communication carried?
```

For example:

|Logical Function|Possible Transport|
|---|---|
|Data Plane|Data Network|
|Management Plane|Management Network|
|Control Plane|Management Network|
|Telemetry Plane|Management Network or Data Network|

Several logical planes can therefore share the same transport infrastructure.

---

## Current Testbed

The current testbed provides a dedicated management network that is separated from the experiment/data network.

A simplified representation is:

```
MANAGEMENT NETWORK
172.20.202.*

SSH
gNMI
SDN control
monitoring
orchestration
possibly sFlow / Kafka
```

separated from:

```
DATA NETWORK
172.20.2.*

TRex traffic
application traffic
experiment traffic
QFX-to-QFX forwarding
```

This separation can provide very stable conditions for telemetry and control traffic because they do not necessarily compete with the experiment traffic.

## Telemetry Transport as a Research Variable

The transport of telemetry is an important part of this thesis.

The telemetry pipeline itself remains logically the same:

```
Physical Network
       |
       v
Telemetry Collection
       |
       v
Kafka
       |
       v
NDT
```

However, the network used to transport the telemetry can be changed.

### Scenario A — Dedicated Management Transport

Telemetry and messaging traffic are transported over the separate management network.

```
Management Network
------------------
gNMI
sFlow
Kafka
Monitoring
Control

Data Network
------------
TRex / Production Traffic
```

This isolates telemetry from the production load.

Advantages may include:

- low telemetry latency
    
- low packet loss
    
- predictable synchronization
    
- stable control communication
    

However, this may represent an idealized laboratory environment.

---

### Scenario B — Shared Data-Plane Transport

Telemetry and messaging traffic share network resources with production or experiment traffic.

```
Shared Network
-------------------------
TRex / Production Traffic
+
gNMI
+
sFlow
+
Kafka Traffic
+
potentially Control Traffic
```

In this scenario, telemetry traffic competes with production traffic for available bandwidth and network resources.

This can affect:

- telemetry latency
    
- message delay
    
- packet loss
    
- Kafka delivery latency
    
- NDT state freshness
    
- synchronization quality
    
- control-loop response time
    

---

## Bidirectional Influence

The interaction can occur in both directions.

### Production Traffic Influences Telemetry

```
Increasing Production Load
           |
           v
Network Congestion
           |
           v
Telemetry Delay / Loss
           |
           v
Older NDT State
```

This can reduce the synchronization quality between the physical network and the NDT.

### Telemetry Influences the Network

At the same time, telemetry itself generates network traffic.

```
More Devices
     +
Higher Telemetry Rate
     +
Flow Data
     +
Kafka Traffic
        |
        v
More Network Overhead
```

At larger scale, this additional traffic may influence the underlying production network.

---

## Project Relevance

The separation between management and data networks is therefore directly relevant to the thesis.

The current testbed offers relatively controlled conditions through a dedicated management network.

A real deployment may instead require telemetry, messaging, control and production traffic to share parts of the same infrastructure.

This motivates experiments investigating:

- dedicated management transport
    
- shared telemetry and production transport
    
- increasing production load
    
- increasing telemetry rates
    
- increasing number of network nodes
    
- messaging overhead
    
- congestion
    
- component failures
    
- NDT synchronization quality
    
- end-to-end update latency
    
- state freshness
    
- reliability
    

The goal is therefore not only to evaluate the telemetry and messaging infrastructure under ideal laboratory conditions, but also to understand how the architecture behaves under conditions that more closely resemble real network deployments.
